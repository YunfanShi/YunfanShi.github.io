### Offline Workspace transaction boundary (source-verified 2026-10-27)

`supabase/migrations/20261025023755_reliable_offline_mutations.sql` shows that `apply_offline_mutation` is not a simple row upsert. It acquires an account-scoped advisory transaction lock, checks an immutable `(user_id, operation_id, kind, payload, request_hash)` receipt, performs the domain mutation, and inserts the source receipt before the same transaction commits. `task.create` uses the operation UUID as the task UUID; `plan.delete` deletes child tasks and the plan; `review.attempt` inserts an immutable attempt and updates the review item's interval, streak, status and next-review time. The source receipt result contains operation identity/hash and confirmation state, but not a complete snapshot of every affected row.

Therefore a post-RPC Azure write would be a cross-database dual write, not an atomic migration. If Supabase commits and Azure fails, the local queue can retry because its source operation ID is idempotent, but it must not treat the source receipt alone as proof that the V5 projection exists. For an account with V5 authority, acknowledgement must require both the source-side receipt (while the source remains authoritative) and the V5 record receipt plus readback hash; projection failure must leave the browser operation retryable. The eventual authority cutover must move the full multi-row transaction and receipt into the Azure/V5 transaction boundary, or provide a durable source outbox with replay and per-row reconciliation before freezing the legacy writer. No such dual-write/cutover code is enabled by this audit.

This source trace narrows ownership questions but is not an implementation or runtime proof. The proposed workspace records/new scopes are not yet connected to client mutations or server projections. These six API owners therefore remain explicit blockers to declaring P0/P1 complete.

## Executive result

The portal does not yet meet the goal of making v5 the only normal sync protocol. The six Schedule scopes cover many Schedule fields, and the current worktree adds a v5 `workspace` namespace for syncable localStorage keys. However, v5 workspace values are still one resource per localStorage key, which is too coarse for keys containing collections. The current local coordinator has a tested atomic migration path for eligible v4 Outbox items and runs v5 before the remaining v4 engine; frozen/ineligible legacy operations remain on v4. Separate IndexedDB databases also contain application state outside the v5 resource model. Do not add `workspace` to the production rollout until the complete data inventory, compatibility bridge and migration tests cover all owners and all remaining operations.

## Safety findings that block workspace rollout

1. The legacy engine still runs for keys/scopes not yet owned by v5. The worktree filters keys only after the v5 field baseline and atomic ownership preparation succeed; this behavior has local tests but no real-device or production evidence.
2. The worktree adds atomic migration for eligible v4 workspace operations. Frozen protocol submissions, unresolved v4 conflicts, local edits newer than the operation, base mismatch, and conflicting v5 operations are deliberately deferred rather than overwritten. The browser coordinator integration and actual remote receipt recovery still need dedicated authenticated end-to-end validation.
3. Server workspace bootstrap copies legacy keys once when a scope head is absent. The examined v5 write path intentionally avoids rebuilding the Schedule projection for workspace writes; no complete v4-to-v5 and v5-to-v4 bridge for arbitrary workspace keys was identified. Do not assume old clients and v5 clients share one version baseline.
4. Generic per-key workspace mapping may reduce the number of records but not the bytes for one large localStorage key. It does not satisfy item-level CUE/task delta for standalone collections.
5. Key-name filtering is not sufficient to establish that allowed JSON values contain no nested credentials or other private material.
6. Fixed in the current worktree: unclassified syncable localStorage keys no longer fall through to a catch-all v5 field. They remain legacy-owned pending an explicit domain mapping; this avoids unsafe generic migration but means P0 coverage is not yet complete.
